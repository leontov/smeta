# Архитектура монорепозитория

Монорепозиторий разделён на два основных приложения и набор общих артефактов данных:

- `apps/mobile` — Flutter-клиент, работающий офлайн и синхронизирующийся с бэкендом при наличии сети.
- `apps/backend` — Node.js/TypeScript API со слоями для ИИ-инференса (через Genkit/Gemini), расчётного движка и экспорта документов.
- `datasets/` — версионируемые нормативные базы и вспомогательные структуры (индексы, матрицы коэффициентов, словари синонимов).

## Потоки данных

1. **Парсинг ТЗ**. Мобильное приложение собирает текст, фото и голос, обрабатывает их локально (OCR/ASR) и формирует описание. При наличии сети запрос расширяется до облачного эндпоинта `/api/estimates` для уточнения с помощью Genkit/Gemini.
2. **Подбор норм**. Без сети используется локальная SQLite-база с поиском по токенам и синонимам. В онлайне сервер подгружает актуальную версию датасета и применяет гибридный скоринг (TF-IDF + эмбеддинги Gemini).
3. **Расчёт сметы**. Клиент вычисляет базовую стоимость и применяет коэффициенты. Сервер предоставляет эталонные расчёты и экспортные документы (PDF/XML/XLSX) по запросу.
4. **Экспорт**. Бэкенд формирует документы (КС-2/КС-3/КС-6а/ССР) и пакеты CommerceML/АРПС, а мобильное приложение умеет хранить их офлайн и делиться через системы 1С/ГИС ЖКХ.

## Безопасность

- JWT (RS256) и RBAC реализованы на бэкенде, мобильный клиент хранит токены в зашифрованном хранилище.
- Все базы на устройстве шифруются (sqflite + SQLCipher), обновления проходят через проверку подписи.
- Аудит и журналирование отправляются в SIEM при синхронизации.
